# ADR 0009 · 检索结果默认裁剪，详情按需从缓存取

- 状态：accepted
- 日期：2026-11-08
- 关联：ADR 0007（WoS 取数方式）、ADR 0008（内核钩子）

## 背景

一次检索能拿到 50 条记录，每条摘要 1000–1300 字符。整包返回约 **2 万 token**，而其中九成
这一轮用不上。

更糟的是"事后取摘要"的默认路径：`detail(url)` 未命中缓存时会重新访问站点——为的是拿
**已经解析过、只是没返回**的数据。50 条就是 50 个网络动作。

## 备选

### 备选 A：维持原样（全部返回）

- 优点：不动契约，调用方不必学新参数。
- 被否理由：每次检索都付 2 万 token；而且"按需取"必然退化成重复抓取，与 ADR 0007
  「零额外请求」的初衷相反。

### 备选 B：只裁剪，不做本地筛选

- 优点：改动最小，一个布尔参数。
- 被否理由：调用方仍要先把 50 条拉进上下文才能排序或筛选；若把排序交给站点（点排序按钮），
  又要多 2 个网络动作。

### 备选 C：裁剪 + 本地后处理 + 详情缓存播种（选中）

- 优点：一次抓取、一次解析，之后全部本地；详情取用零请求。
- 被否理由：`SearchQuery` 增加 4 个字段，属契约变更——本文即为记录它而写。

## 决策

1. `SearchQuery` 增加 `include_abstract`（**默认 `false`**）、`sort_by`（`none|citations|year`）、
   `min_citations`、`sources_only`。四者都在解析**之后**执行，不产生任何浏览器动作。
2. `ScholarService.search` 在**过滤与截断之前**，把每条记录按 `detail:<url>` 播种进缓存。
   于是 `detail(url)` 命中缓存，**零网络动作**返回完整记录（含摘要）。
3. `min_citations` 对**引用数未知**的记录保留而非丢弃：部分结果视图根本不下发引用数
   （WoS 的 `runQuerySearch` 就是），过滤掉会让"没测"看起来像"没有"。

## 后果

- 默认返回变为短清单（title / authors / source / year / volume / issue / pages / doi /
  keywords / citations / url / doc_type），摘要需显式索取。
- **对所有渠道一致生效**——参数是工具级的。但对 CNKI 它是**空操作**：CNKI 的列表页从不
  产出摘要（`parse_search` 根本不设 `abstract`），摘要只在详情页。WoS 的列表页自带摘要，
  所以这个开关只在 WoS 上真正省 token。
- 两个渠道"取摘要"的代价因此不同：CNKI 走 `detail(url)` 要真实访问一次详情页；WoS 的
  `detail(url)` 命中检索时播种的缓存，**零请求**。播种只针对**自带摘要**的记录——否则 CNKI
  的列表行会把 `detail` 喂成一份比详情页更残缺的记录（0.6.1 修的就是这个）。
- 每次检索多写约 50 条缓存记录；`Cache` 的容量与过期策略未改。
- **站点端请求数不变**（仍是 3 个/检索），因此风控剖面不变。
- 若日后要在返回里带上影响因子，必须改 `schemas/record.json`（`additionalProperties: false`），
  那是另一个 ADR。
