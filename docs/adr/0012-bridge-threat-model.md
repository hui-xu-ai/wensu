# ADR 0012 · 浏览器桥的威胁模型与宿主任信边界

- 状态：accepted
- 日期：2026-11-09
- 关联：ADR 0002（只读约束）、ADR 0003（频率与风控）、ADR 0006（不做第三方入库）

## 背景

一次独立审计提出（编号 C5）：native host 的 TCP 端点凭据 `bridge.json` 落在
「任何低完整性进程可写」的目录里，且宿主自身不做频率限制——于是同机的恶意或失控进程
可以改写 `bridge.json` 把内核导向伪造端点，或读出 token 直连宿主发动作，从而绕过
「3000 ms 间隔 / 每日 300 / 并发 1」这些承诺。

这条是否成立、有多严重，取决于**威胁模型**。此前仓库从未把威胁模型写下来，
所以这条既无法被确认为缺陷，也无法被排除。本文补上那块地基。

## 威胁模型

### 信任边界之内（本工具为其设计）

- **同一个 Windows 用户会话**里的正常进程：CLI、内核、浏览器扩展、native host。
- 用户自己的脚本与终端。它们本来就能读 `%LOCALAPPDATA%`、能改环境、能起进程。

### 信任边界之外

- 其他用户（Windows 用户隔离已经挡住）。
- 远程站点与网络上的中间人（域名白名单 + https 已经挡住）。
- **浏览器渲染进程被攻破后、以低完整性运行的进程**。

### 关键事实

1. 宿主由浏览器经 native messaging 启动，**天然是低完整性进程**。
2. 宿主必须写 `bridge.json`（port + token），而低完整性进程只能写低完整性对象——
   所以那个目录**必须**允许低完整性写入，否则宿主无法告知内核自己在哪。
3. token 每次宿主启动随机生成（`secrets.token_urlsafe(24)`），不跨进程复用。
4. 宿主只做 `validate_request`：动词封闭、参数封闭、域名白名单。**它不做限速**，
   限速在内核（`core/policy.py`）。
5. 扩展只有 `nativeMessaging` + `tabs` 权限。**没有** `downloads`、`debugger`。

## 备选

### 备选 A：接受，并把边界写清楚（选中）

- 前提是「浏览器渲染进程已被攻破」——那已经是浏览器沙箱逃逸级别的事件。
- 在那个前提下，攻击者**能读**的东西远不止 `bridge.json`：缓存、配额、审计日志，
  以及用户目录下的其余文件。守住这一个文件不会改变局面。
- 他**不能**借此做比读缓存更坏的事：宿主只接受九个封闭动词、只允许 manifest 声明的域名，
  而下载、写第三方库这两类动作**根本不存在**（ADR 0002 / 0006）。
- 危害收敛为**数据完整性**（伪造题录进入缓存或导出），不是越权访问。

### 备选 B：宿主侧自己也加限速

- 否。理由与 ADR 0003 一致：限速的真相源只能有一份，两份必然漂移——
  本仓库已经为「双端各持一份规则」付过两次代价（`docs/incidents.md` 有记录）。
- 宿主加限速还会带来一个更坏的后果：内核与宿主各算各的配额，用户看到的剩余次数与实际不符。

### 备选 C：把 `bridge.json` 移出低完整性目录

- 否。宿主是低完整性进程，写不了未降级的目录——那会让宿主彻底无法公布端口。
- 换一条路（宿主把 port/token 通过 native messaging 回传给扩展、扩展存 `chrome.storage`）
  等于重写桥协议，收益仅是「同机低完整性进程读不到 token」，成本与风险都不成比例。

### 备选 D：给宿主加身份认证（nonce 或多因素）

- 否。同用户下 nonce 同样写在可读文件里，绕不开同一前提；真要做只能引入用户态密钥库
  或操作系统凭据保护，那是另一个项目的工作量。

## 决策

**接受备选 A。** 现有缓解保持不变并在此登记：

| 缓解 | 位置 |
|---|---|
| token 每次宿主启动轮换 | `native-host/main.py`（`secrets.token_urlsafe`） |
| 动词封闭（九个） | `core/contracts.py` `VERBS` |
| 参数白名单 | `core/params.py` |
| 域名白名单，**内核与宿主双端各校验一次** | `core/policy.py` + `adapters/bridge/policy.py` |
| 无下载、无第三方入库 | ADR 0002 / 0006，动词集合里根本没有这类动作 |
| 扩展最小权限 | `extension/manifest.json`（只有 `nativeMessaging` + `tabs`） |

## 后果

- **明确不在范围内**：防住同用户下已取得执行能力的恶意进程。真要防，需要签名校验或
  用户态密钥库，成本远超本工具的价值。
- 因此 C5 从「待修缺陷」降为「已记录的接受风险」。它不应再出现在后续审计的
  critical 列表里——除非威胁模型本身改变（例如将来允许跨用户、或加入下载能力）。
- 若将来确实要加下载能力（目前是被 ADR 0002 禁止的），**必须重开本文**：
  下载会把「数据完整性」风险升级为「实际获取被限制资源」。
- 审计同时指出的「宿主管道无长度上限」「错误 token 也回包」属于健壮性细节，
  另在 `docs/incidents.md` 或后续提交中处理，与本决策无关。
