# 0023 · 动作节奏按性质分级，并躲开后台标签的定时器粒度

**状态**：已接受并实现（2026-11-24，0.14.4）
**相关**：ADR 0005（频率）、ADR 0021（最小间隔 900ms）、ADR 0018（工作页在独立窗口）

## 背景

一轮 WoS 检索实测 **48.2 s**，其中"导出对话框"这一段（4 次点击 + 4 次等待）约 **14 s**。用户手里的
实测是：**点导出 → 弹窗 → 填范围 → 点导出 BibTeX，整个过程 1–3 秒**，且反复测试都没触发风控。

拆开看，那 14 s 里没有一毫秒是站点在加载，两个原因都在我们这边：

1. **统一的动作间隔**。`wait_turn()` 给每个计费动作都套 `min_interval_ms`（当时 900ms），
   而这一步全是**页内表单操作**——页面早就加载完了，间隔保护的"请求频率"在这里不存在。
2. **后台标签的定时器粒度**。工作页为了不打扰用户，放在**非聚焦窗口**里；Chrome 对后台标签的
   `setTimeout` 按 ~1 秒对齐。`humanClick` 里原本有 4 个 40–200ms 的小睡，在后台标签里每个都被抬成
   约 1 秒 → 一次点击实测 **~2.0 s**。这条我们自己的代码里早有记录
   （`plan_search.py: SLEEP_REPLY_MARGIN_MS = 2_000 —— 后台标签对齐到一秒"），只是没往这里想。

## 决定

**A. 计划按性质声明节奏。** `Plan` 增加 `pacing: "network" | "ui"`（默认 `network`）：

- `network`：会提交检索、打开页面的计划，沿用 `min_interval_ms`（ADR 0021 的 900ms）；
- `ui`：只驱动**已打开页面**上的控件（对话框、下拉、输入框）的计划，用
  `HARD.ui_interval_ms = 150ms` + 抖动。

导出计划声明 `pacing="ui"`，并把其中四个"等到了还再睡一觉"的 `settle`（600–900/300–450/200–350）
收成 60–120ms。

**配额计数不变**：`wait_turn()` 仍然是"一个动作一个额度单位"，本次只改它睡多久，不改怎么记账，
`quota_charged` 仍是 8。

**B. 页内操作只留一次小睡。** `humanClick` 的 4 次小睡合并成 1 次、`humanType` 的 2 次合并成 1 次。
事件顺序不变（pointerover→…→mouseup→click），只是不再为"拟人"付 3–4 个被放大的定时器。

## 备选方案

| 方案 | 结论 |
|---|---|
| A. 一切照旧，只把 `min_interval_ms` 再往下调 | 拒绝：页内操作根本不需要网络级间隔，继续调低会连真正需要保护的提交也一起松掉 |
| B. 导出时把工作窗口置前，避免后台节流 | 拒绝：会抢用户焦点，比慢更烦人 |
| C. 计划级 `pacing` + 减少页内小睡（采纳） | 采纳：改的是"给谁加间隔"，而不是"间隔多长" |
| D. 用 `requestAnimationFrame` 轮询代替定时器 | 拒绝：后台标签里 rAF 根本不跑，比定时器更糟 |

## 风险与回退

- 风险：页内操作从 900ms 降到 150ms，理论上让"点击脉冲"更密集。用户的实测（导出全程 1–3 秒，
  甚至 1 秒）没有触发风控；且这些动作不产生新的页面请求。
- **回退阈值**：7 天内若 WoS 导出流程出现任何 `blocked`/`RISK_CAPTCHA`/403，把
  `ui_interval_ms` 改回 900 并记录 incident。
- 观察项：`quota_charged` 应恒为 8（本次不改计费）；导出段耗时应从 ~14 s 降到 ~5 s。

## 影响

- 用户感知：同样的检索动作，页内一段不再按"网络节奏"等待。
- 代码：`contracts.Plan.pacing`、`config.HARD.ui_interval_ms`、`policy.wait_turn(interval_ms=)`、
  `planner` 传递、`plan_export` 声明与 `settle` 收紧、`content/actions.js` 两处小睡合并。
- 注意：**扩展侧改动需要重新加载扩展**才生效；只升级 Python 包只拿到计划侧的一半收益。
