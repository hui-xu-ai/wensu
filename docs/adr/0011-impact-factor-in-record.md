# ADR 0011 · 记录带上期刊影响因子

- 状态：accepted
- 日期：2026-11-08
- 关联：ADR 0010（影响因子筛选）、ADR 0009（短清单）

## 背景

ADR 0010 把影响因子用于**筛选**，但明确写了「只看数值需要改 `record.json`，那是另一个 ADR」。
现在需要这个值本身：调用方要自己判断「这篇值不值得读」，而不是只能给一个阈值。

## 备选

### 备选 A：维持现状，只做筛选

- 优点：不动 `record.json`，其他渠道零影响。
- 被否理由：调用方拿不到数值就无法做「先看 IF 再决定读哪篇」的判断，只能反复调阈值试。

### 备选 B：`record.json` 加可选 `impact_factor`（选中）

- 优点：一个字段、语义直白；可选，所以不破坏既有渠道；导出层无需改动（RIS/EndNote 无此字段）。
- 被否理由：`record.json` 是公开契约，加字段永远是契约事件——本文即为记录它而写。

### 备选 C：加嵌套的 `metrics` 对象（影响因子、五年影响因子、分区、JCR 年份）

- 优点：一次把 JCR 的常用维度都带上。
- 被否理由：这些都是 Web of Science 专属，塞进公共契约会让「通用题录」变成「WoS 题录」。
  真要做，应该另开一个渠道专属的扩展点，而不是往主契约里堆。

## 决策

1. `schemas/record.json` 增加 `"impact_factor": { "type": ["number", "null"] }`；
   `Record` 增加同名可选字段，`to_dict()` 一并输出。
2. WoS 渠道在解析时把 `jcrKey` 命中的 `ImpactFactor` 填进去；`jcr` 块按批下发，
   所以仍是「先收全部 jcr，再建记录」两遍走。
3. CNKI 恒为 `null`——它没有这个概念，这比编造一个「0」诚实。
4. `min_impact_factor` 的筛选语义不变：未达标或无指标的记录整条丢弃。

## 后果

- `record.json` 多了第 18 个字段。旧缓存因为缓存键含版本号会自然失效，不做迁移。
- 导出不受影响：RIS 的 `IF` 不是标准标签，EndNote 也没有对应字段，宁可不写也不写错。
- 调用方现在可以做「先按 `min_impact_factor` 收窄，再按返回的 `impact_factor` 排序」这类组合，
  两者都在本地完成，零网络动作。
- 若日后要带分区（Q1–Q4）或五年影响因子，走备选 C 的扩展点，不要再往主契约里加字段。
