# 0021 · 网络动作最小间隔 3000ms → 1200ms

**状态**：已接受并实现（2026-11-24，0.14.4）
**相关**：ADR 0005（频率与配额）、ADR 0020（记录范围导出）、`docs/incidents.md`

## 背景

ADR 0005 定的最小间隔是 3000ms，`AGENTS.md` 把它写成不可协商的硬下限，只允许收紧。当时没有
实测数据，取的是保守值。

2026-11-24 的端到端实测（WoS 检索 + 通读，见 `D:\Python\DeepSeek\Test\wensu-测试审查报告.md`）
给出了两个事实：

1. **一轮 WoS 检索是 8 个计费动作**（`goto`、`type`、6 次 `click`；`wait_for`/`sleep` 不计费），
   3s 间隔就是 **24s 的纯等待地板**，审计实测整轮 ~40s。用户体感"检索太慢"直接来自这里。
2. **站点侧没有压力信号**：当日 8 次完整检索、数十次页面动作，没有任何 captcha/403/`blocked`
   事件（审计 `action` 事件全 `ok: true`）。

同一轮测试里，用户用秒表人工观察站点自身的响应节奏：**每次动作间 0.9–1.6s 的停顿完全正常**
（菜单/控件触发在页面内完成，通常 <300ms），瓶颈从来不是站点，而是我们的固定间隔。

## 决定

- `HARD.min_interval_ms`：`3000` → **`1200`**（`src/scholar_search/config.py`）。
- 抖动保留：每次 `wait_turn` 仍是 `min_interval_ms + jitter`，避免整齐的等间隔波形。
- **不变**：并发 1、单次 ≤3 页、每日 ≤300 次动作、`wait_turn` 的语义（一个计费动作一个配额单位）、
  计价（`quota_charged` 仍按实际计费动作数）。
- ADR 0005 的其余条款继续有效；本条只是把最小间隔这一项放宽，并给出回退阈值（见下）。

## 备选方案

| 方案 | 结论 |
|---|---|
| A. 保持 3000ms | 拒绝：24s 地板 + 页面加载 = 每轮 40s，用户已明确无法接受 |
| B. 按渠道分别设（WoS 1200 / CNKI 3000） | 拒绝：多一套配置与一套测试，收益不确定；CNKI 若真的更敏感，先按 C 观察再单独收紧 |
| C. 1200ms + 抖动 + 回退阈值（采纳） | 采纳：单轮 ~20–22s，压力仍是"1 请求 / ≥1.2s"，日上限不变 |
| D. 不设间隔，靠站点报错退避 | 拒绝：把"被站点惩罚"当成控制手段，违反 ADR 0005 的精神，也给用户带来封禁风险 |

## 风险与回退

- 风险：更密的请求可能触发 WoS 的软限流（表现为页面变慢、偶发 403，或 `page_read` 更容易撞
  质询）。
- **回退阈值（可执行）**：实施后 7 天内，若审计里出现 **≥1 次**风险信号（`blocked`、
  `RISK_CAPTCHA`、403），立刻把 `min_interval_ms` 改回 `3000`，重跑一轮对照，并在
  `docs/incidents.md` 记一条。
- 观察项：同一检索式的单轮耗时（应 ~20–22s）、审计里 `duration_ms` 的分布、`blocked` 计数。

## 影响

- 用户感知：WoS 一轮检索从 ~40s 降到 ~20–22s；配额消耗不变。
- 代码：`config.py` 一个默认值、`test_channel_contract.py` 一条断言、`skills/scholar-search/SKILL.md`
  的耗时预期、`.dsh-memory` 里的手写记录。
- 不改动词、不改契约、不改计价方式。
